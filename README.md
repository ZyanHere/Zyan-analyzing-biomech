# Real-time biomechanical analysis from a single webcam

Twelve joint angles computed live from one fixed monocular camera, each shown with an
explicit judgement about whether it can be trusted.

The system measures **elbow flexion, knee flexion, shoulder flexion/extension, shoulder
abduction/adduction, hip flexion/extension and ankle dorsi/plantarflexion**, on both
sides. It runs at **30 FPS on a live camera** (the camera's own ceiling; the pipeline
sustains 39) with **24.7 ms end-to-end latency**.

The part that took the most work is not the angles. It is the refusal: a single camera
cannot measure every joint from every viewpoint, and the system says so per measurement
rather than reporting a confident wrong number. Ten of twelve measurements are withheld
when the subject faces the camera, and that is correct behaviour, not a bug.

---

## Quick start

```bash
python -m venv .venv
.venv/Scripts/activate
pip install -r requirements.txt
pip install -e biomech
```

On Linux or macOS the activate line is `source .venv/bin/activate`.

**Python 3.14 is required** by the pinned `mediapipe==1.0.1` build. Verified on Windows 11
with Python 3.14.7.

Download the pose model (44 MB, not in the repository):

```bash
curl -L -o biomech/models/pose_landmarker_full.task https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_full/float16/latest/pose_landmarker_full.task
```

Run it:

```bash
biomech --source camera
```

**No webcam? It still runs.** The application and every landmark-based finding replay from
recorded data, with no camera and no model:

```bash
biomech --source landmarks --path biomech/research/fixtures/sessions/session.jsonl
```

Six investigation scripts need video, and those recordings were images of the subject, so
they were deleted rather than published — see
[research/experiments/README.md](biomech/research/experiments/README.md) for which ones and
how to supply your own, and [DATA.md](biomech/docs/DATA.md) for why.

## Standing in the right place

This is the one thing that decides whether the system works for you, and it is a property
of single-camera measurement rather than of this implementation.

| You are | Measurable | Withheld |
|---|---|---|
| **Side-on** (shoulder line edge-on to the lens) | elbow, knee, shoulder flexion, hip, ankle — 10 of 12 | shoulder abduction, both sides |
| **Facing the camera** | shoulder abduction, both sides | the other 10 |
| In between (30–45°) | nothing | all 12 — the plane is ambiguous |

A joint angle in a plane is only measurable when that plane faces the lens. Flexion happens
in the sagittal plane (side-on); abduction happens in the frontal plane (face-on). **One
camera cannot present both at once**, so at most 10 of 12 are ever valid simultaneously.
The orientation gate measures your rotation from the 3D shoulder axis and tells you which
way to turn.

Also:

- **Stand 1.5–2.5 m away**, full body in frame. Detection fails below roughly 63 px of
  shoulder width.
- **Light the subject from the front.** The camera is held at a fixed short exposure to
  reach 30 FPS, which costs about 2.6× image brightness; in a dim room the legs lose
  confidence and knee measurements are withheld.
- Camera height barely matters (under 2° of effect), so do not spend time on it.

## Reading the display

Each row shows a measurement, its value, and its status:

```
elbow         L   42 flexion                  OK
knee          L    -                          turn side-on to the camera
shoulder abd  R    -                          low confidence (0.41)
```

- **A named direction, never a minus sign.** 15° of shoulder extension reads
  `15 extension`, not `-15`. A reviewer should not have to know the sign convention.
- **`-` plus a reason** means the system declined to answer. The reason is an instruction
  where one applies (`turn side-on`) and a diagnosis where none does (`low confidence`).
- Four independent signals can withhold a value: landmark visibility below 0.55, bone
  length varying more than 6% on one side, the wrong plane presented, or no person found.
  Bone-length *asymmetry* is shown as a warning but never blocks a measurement — it has a
  false-positive mode tied to camera height.

**The live figure is the camera's ceiling, not the pipeline's.** The same code on the same
frames reaches 39 FPS from a file, so the honest statement is three numbers rather than
one: source 30 FPS, pipeline throughput 39 FPS, displayed 30 FPS.

Where a 25.2 ms frame goes:

```
inference   19.8 ms   79%     the pose model
render       2.9 ms   11%     skeleton, panel, compositing
biomech      0.8 ms    3%     12 angles, 4 validity signals, smoothing
other        1.7 ms    7%     capture, colour conversion, loop
                              against a 33.3 ms budget: 24% spare
```

**The model is the system.** Everything this project adds on top of pose estimation —
twelve measurements, the validity layer, One Euro smoothing on 33 landmarks, the whole
display — costs 3.7 ms of a 25.2 ms frame.

### It is sensitive to CPU contention, by a lot

| Competing CPU-bound processes | Displayed FPS | Inference p50 |
|---|---|---|
| 0 | 37.4 | 20.0 ms |
| 2 | 29.1 | 26.9 ms |
| 4 | 22.3 | 35.1 ms |
| 8 | 14.9 | 48.5 ms |

Inference is multi-threaded and competes for the same cores as everything else, so it
degrades 2.4× between an idle and a half-loaded machine. **Close other applications before
measuring.** This sweep exists because an earlier benchmark of this system reported 28.6
FPS and was briefly recorded as a shortfall; it was two background processes.

### Reproducing these numbers

The recorded videos these runs used are **not in the repository** — they are footage of the
subject and this repository is public. So the full-pipeline rows need your own recording:

```bash
biomech --source camera --duration 60 --record-video my_session.mp4 --metrics-out live.json --label camera-full-ui
biomech --source video --path my_session.mp4 --metrics-out replay.json --label my-replay
```

The first command measures the live path and keeps the frames; the second replays those
identical frames, which is how throughput is measured without the camera's 30 FPS ceiling
in the way. `--bench-inference my_session.mp4` times the model alone.

What *does* reproduce immediately from a clean clone is everything downstream of the model,
because landmark recordings are coordinates rather than images and are committed:

```bash
biomech --source landmarks --path biomech/research/fixtures/sessions/session.jsonl --no-ui --metrics-out downstream.json --label replay
```

That reports **processing** latency rather than end-to-end, because a recording has no
capture instant — the application knows the difference and labels it.

Results live in [`biomech/docs/benchmarks/`](biomech/docs/benchmarks), each carrying the
hardware and the complete configuration that produced it. The table above is generated
from those files rather than typed, and the generator can prove the README is current:

```bash
python biomech/tools/performance_table.py --check
```

## Accuracy, including what is not validated

Two kinds of validation, answering different questions.

**Synthetic (all twelve):** a skeleton is built at known joint angles by forward
kinematics, projected to 2D, and measured. This tests whether the geometry is right, with
no camera or model involved. Worst error across all measurements, both sides, every
orientation: **0.000000°**. That eliminates the maths as an error source. It says nothing
about the model.

**Physical (three attempted):** held poses against an external reference.

| Measurement | Synthetic | Physical | Result |
|---|---|---|---|
| Elbow flexion | exact | **yes** | 2D reads 3.1° at an anchored 0°; 3D MAE 12.8° side-on |
| Shoulder flexion | exact | **yes** | **2D MAE 2.7°**, bias +0.5° (2 anchored poses) |
| Knee flexion | exact | **attempted, refused** | visibility 0.37–0.49, below the 0.55 threshold |
| Hip flexion | exact | no | — |
| Shoulder abduction | exact | no | — |
| Ankle | exact | no | — |

**Six of twelve measurements ship with synthetic validation only.** Saying so precisely is
more useful than implying otherwise. Reference error was ±5° for the printed protractor and
±8° for anatomically anchored poses, and those bounds are the floor under any number above.

### The knee could not be validated, and that is a result

```
2D sagittal validity  requires  side-on
knee landmark quality requires  the legs not overlapping
side-on               causes    the legs overlapping
```

The orientation that makes a 2D knee measurement valid is the same orientation that makes
one leg occlude the other. **The system detected this itself and withheld the value** — the
refusal came from the validity layer, not from someone noticing afterwards. A confident
wrong knee angle would have been a worse outcome than no knee angle.

### Why 2D, when the model also offers 3D world coordinates

Measured at six known elbow angles: 3D compresses movement by 23% even at its best (bend
150°, it reports 125), and the compression factor *moves with body orientation*, so a
per-subject calibration breaks as soon as the subject turns. 2D's failure mode is different
in kind — it fails only when the measurement plane is not facing the lens, which is
**detectable at runtime and correctable by the user**. A detectable, instructable failure
beats an invisible 23% error.

The one place 3D is used is deciding *which way the subject is facing*, because that needs
only the direction of the shoulder axis, not the magnitude of a limb angle.

## Known limitations

1. **At most 10 of 12 measurements at once.** Sagittal and frontal planes cannot both face
   one lens. Not fixable without a second camera.
2. **Knee flexion is unvalidated**, and is withheld in exactly the pose that would validate
   it. See above.
3. **Six measurements have synthetic validation only** — hip, abduction and ankle, both
   sides.
4. **The ankle's landmarks are geometrically wrong.** The model places heel and toe 12–14 cm
   apart where the true distance is about 25 cm. The `heel → foot_index` definition used
   here has zero bias and 18% less noise than the alternatives, but it is built on a short
   segment and its absolute accuracy is unknown.
5. **One subject, one camera, one machine.** Every number here was measured on a single
   person with a single low-cost webcam on a single laptop. Generalisation across body
   types, cameras and hardware is untested.
6. **Smoothing shaves peaks by about 10%.** For true range-of-motion endpoints, run with
   `--no-filter`.
7. **No absolute scale.** There is no camera calibration, so nothing is reported in
   centimetres — only angles, which are scale-free.
8. **The `heavy` model is rejected, unexplained.** It drifts 21.6° out of plane where
   `full` drifts 4.2°. The cause was never found, so it is not used.
9. **The bone-length validity signal is motion-sensitive.** It judges a reconstruction by
   how much a segment's length varies over a 30-frame (~1 s) window. During rapid movement
   that window spans genuinely different reconstructions, so the variance rises and the
   measurement is withheld — on 57–87% of frames while a limb is moving fast, against
   0–25% while still. **Hold a pose for about a second and the value returns**, stable:
   abduction held horizontal reads 80–83° with a 6° spread.

   The threshold was **not** changed. The same signal is the only one that caught a 147°
   knee error in a seated pose, where landmark confidence read 0.88 and no visibility
   threshold would have flagged it. Loosening it to smooth out movement would risk losing
   the one failure nothing else detects.

   This is a real tension and worth naming: a biomechanics tool is least willing to answer
   while the subject is moving, which is when the measurement is most wanted.

## Command reference

| Flag | Purpose |
|---|---|
| `--source camera\|video\|landmarks` | frame origin (default `camera`) |
| `--path PATH` | the file, for `video` or `landmarks` |
| `--device N` | camera index (default 0) |
| `--model lite\|full\|heavy` | pose model (default `full`) |
| `--running-mode video\|image` | `video` tracks between frames, 2.4× faster |
| `--record-landmarks PATH` | write a replayable JSONL session |
| `--record-video PATH` | **also** write raw video — this records the subject |
| `--metrics-out PATH` | write timings, hardware and config as JSON at exit |
| `--label NAME` | name the run inside that JSON |
| `--no-ui` | headless, for benchmarking |
| `--duration N` | stop after N seconds |
| `--no-filter` | disable smoothing; use for true peak range of motion |
| `-v, --verbose` | debug logging |
| `--probe` | report what the camera actually delivers, then exit |
| `--bench-inference VIDEO` | time the model alone, nothing else |

Three source modes, because they answer different questions:

| Source | Runs the model? | Good for |
|---|---|---|
| `camera` | yes | live use; true end-to-end latency |
| `video` | yes | comparing **models** — identical images in |
| `landmarks` | **no** | comparing everything **downstream** of the model, deterministically |

A landmark recording cannot compare pose models, because its landmarks are already one
model's output. That distinction is why both replay modes exist.


Short on time? [BEYOND_THE_BRIEF.md](biomech/docs/BEYOND_THE_BRIEF.md) is a five-minute
read covering the parts worth a reviewer's attention. Otherwise start with
[ARCHITECTURE.md](ARCHITECTURE.md) for the design, or
[FINDINGS.md](biomech/docs/FINDINGS.md) for the evidence behind it. Every tuned constant in
`config.py` carries the finding number that set it:

```python
# At 0.50 a 76 deg error slipped through at 0.52 (F37).
min_visibility: float = 0.55
```

**`src/` never imports from `research/`.** The investigation's scripts are kept because
they are the evidence, not because they are production code, and they are not held to the
same standards. Where logic exists in both, a synthetic audit runs against each copy to
prove they agree — currently to 0.000000000°.

## Data in this repository

It contains recorded data of one human subject — the author, consenting. Five landmark
recordings (15.8 MB) are committed because they are the evidence behind every finding and
they are what lets the application run without a webcam. They are **coordinates, not
imagery**: 33 body landmarks per frame, no photograph of anyone.

The nine video and still recordings were **never committed** — `.gitignore` caught them from
the first commit, verified against git history rather than only against the disk. That is
also why the performance rows above need your own recording to reproduce.

`--record-video` is off by default and logs a warning when enabled, because video of a
subject is a different category of thing from coordinates.

Full reasoning, the trade-off, and the planned action in [DATA.md](biomech/docs/DATA.md).

## Development

The test and lint tools are a separate extra, so running the application does not pull
them in:

```bash
pip install -e "biomech[dev]"
cd biomech
python -m pytest
python -m ruff check src tests tools
```

Tests mirror `src/` one-to-one. The load-bearing ones are in `tests/synthetic.py`, which
builds a skeleton at known angles by forward kinematics — that is what makes "exact to
0.000000°" a measurement rather than a claim.
